This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NotchShelf is a macOS menu-bar utility (pure AppKit, no SwiftUI) that lets users stash files by dragging them onto a floating panel under the MacBook notch, then drag them back out to Finder/apps. Stash lives at `~/Library/Application Support/NotchShelf/Stash`. User-facing strings are in Traditional Chinese — keep new UI text consistent with that.

## Build & run

```bash
./build.sh          # swift build -c release → assemble the bundle → ad-hoc codesign → install to /Applications
open /Applications/NotchShelf.app
```

For a quick compile check: `swift build`. There are no tests or linters. Requires only Xcode Command Line Tools; SwiftPM executable target, macOS 13+, no dependencies.

The app has no `@main`/SwiftUI — `main.swift` manually creates `NSApplication` with `.accessory` activation policy (no Dock icon) so it can be built as a plain SwiftPM executable and wrapped in a bundle by `build.sh`. `Resources/Info.plist` and `Resources/AppIcon.icns` are copied into the bundle by the script.

`build.sh` assembles straight into `/Applications/NotchShelf.app` and leaves no `.app` in the repo — a second copy of the same app shows up twice in Alfred/Spotlight and confuses login items. It updates the bundle in place rather than deleting it, so the path stays stable. Override the destination with `INSTALL_DIR=… ./build.sh`. The icon is generated by `./make-icon.sh` (CoreGraphics → iconutil); the `.icns` is checked in, so a normal build doesn't need to run it.

## Architecture

Single module in `Sources/NotchShelf/`, ~6 classes wired together at launch by `AppDelegate` (also owns the status-bar menu):

- **ShelfStore** — disk + model layer. Owns the stash folder, `items: [URL]` (newest first), and the `removeAfterDrop` UserDefaults setting. All mutations go through `reload()`, which fires `onChange` → the view rebuilds its chips. A `DispatchSource` watcher on the stash folder (`startWatching()`, debounced 0.2s) also triggers `reload()` for changes made behind our back — Finder tidying, or a drop destination that consumed the plain file URL and moved the file itself.
- **NotchWindowController** — owns the `NotchPanel` (a borderless, non-activating `NSPanel` that can never become key/main), computes collapsed/expanded frames from the target screen's notch geometry (`safeAreaInsets` / `auxiliaryTopLeftArea`), and animates between them.
- **ShelfRootView** — panel content view; the drag-*in* target, hover-driven expand/collapse logic, and the **selection** (`selectedURLs: Set<URL>`, keyed by URL so it survives chip rebuilds; click toggles, Shift-click ranges from `selectionAnchor`, marquee/rubber-band from any empty spot with Shift adding to the existing selection, background click clears, header buttons 全選／移除所選). Uses manual frame layout in `layout()` (non-flipped coordinates, offsets measured from the top).
- **ShelfItemView** — one chip per stashed file. Only draws itself and tells the root view about clicks (`chipClicked`) and drags (`beginDrag`). Dragging a selected chip drags the whole selection.
- **ShelfDragCoordinator** — the drag-*out* source (`NSDraggingSource` + `NSFilePromiseProviderDelegate`) for one or many files, owned by the root view for the app's lifetime. `StashFilePromiseProvider` (same file) is the promise provider subclass that also advertises `public.file-url`.

### Invariants that are easy to break

**Drag-out is a safe move.** Drag-in always copies (originals untouched). Drag-out uses `NSFilePromiseProvider`, and when `removeAfterDrop` is on, the stash copy is deleted only inside the promise's `writePromiseTo` completion handler — i.e. only after the destination has fully received the bytes. Do not move that deletion into `draggingSession(_:endedAt:)` (that path only handles the Trash `.delete` case and a `.move` reload); doing so reintroduces a data-loss race on large files.

**Every dragged item also carries the real file URL, *after* the promise types.** `StashFilePromiseProvider` appends `.fileURL` to `writableTypes` so destinations that don't speak promises (cmux, Ghostty, iTerm2, Terminal, most Electron apps) accept the drop; AppKit synthesises the legacy `NSFilenamesPboardType` from it too. Keep the promise types first — a destination that takes the URL gets the stash path and nothing is copied, so nothing is deleted, whatever `removeAfterDrop` says. Because a URL-consuming Finder may move the real file itself, the source operation mask offers `.move` only when `removeAfterDrop` is on; the folder watcher then updates the shelf. Since the drag-out pasteboard now matches the drag-in registered type, `ShelfRootView`'s drop methods reject drags whose `draggingSource` is our own coordinator.

**The promise delegate must outlive the chips.** `NSFilePromiseProvider` holds its delegate weakly and a promise whose delegate is gone is silently never written. Chips are torn down on every `reload()`, and in move mode the first of several files to finish triggers one — so the delegate/source is the long-lived `ShelfDragCoordinator`, never a `ShelfItemView`. The per-file URL travels in `provider.userInfo`.

**Hover expand/collapse is deliberately hardened against flicker.** Several pieces cooperate and each guards a specific failure mode:
- The tracking area is created once with `.inVisibleRect` and never rebuilt — rebuilding it during the frame animation fires spurious enter/exit storms.
- While animating, enter/exit events are ignored (`setAnimating`); on completion `reconcileHoverState()` checks the cursor's real position.
- Collapse is debounced (`scheduleCollapse`, ~0.12s) and re-verifies the cursor position (with a few px tolerance for the top screen edge) before actually collapsing.
- `controller.isDraggingOut` and `isDragInside` both veto collapse; after a drag-out ends the item view must call `scheduleCollapseAfterDragOut()` because no `mouseExited` will fire.

**The panel never takes focus.** `NotchPanel` overrides `canBecomeKey`/`canBecomeMain` to false, and every clickable view overrides `acceptsFirstMouse` to respond without activating. New interactive subviews need the same `acceptsFirstMouse` override or first clicks will be swallowed. This also means there are no key events: selection is mouse-only (no ⌘A), which is why the header has explicit 全選／移除所選 buttons.

**Click vs. drag on a chip.** `ShelfItemView.mouseDown` records the press without calling super (so the root view never sees it and can't start a marquee), `mouseDragged` past ~4px hands off to `ShelfRootView.beginDrag`, and `mouseUp` counts as a click only if no drag consumed the press.

**Marquee selection lives on the root view and is tracked in stack (document) coordinates.** Presses on empty space reach `ShelfRootView` either directly (its `hitTest` reroutes hits on `bgView` and the labels to itself) or through the responder chain from the scroll view's clip/stack views — do not reroute those two in `hitTest`, or scroll-wheel events stop reaching the scroll view. The band rectangle and chip frames are compared in the stack's coordinate space so `stack.autoscroll(with:)` mid-sweep doesn't shift the anchor; the visual `marqueeView` is a root subview clipped to `scrollView.frame`. While `isMarqueeTracking`, collapse is vetoed the same way as `isDragInside`/`isDraggingOut`, and `mouseUp` calls `scheduleCollapse()` because no `mouseExited` is guaranteed after a mouse drag. A press that never moves clears the selection on `mouseUp`, not `mouseDown`.

**The panel background is opaque black on purpose.** The expanded panel overlaps the menu bar on both sides of the notch, and on macOS 26 the menu bar is transparent. Any translucency lets the wallpaper and status icons bleed through as a tinted band beside the notch's rounded corner, which reads as a bite taken out of the panel. Solid black merges notch and panel into one shape; don't reintroduce alpha here.

**Never put a `cornerRadius` on a view that has overflowing subviews.** On macOS 14+ AppKit flips `clipsToBounds` (and the layer's `masksToBounds`) on as soon as a layer-backed view's layer gets a non-zero `cornerRadius` — verified on macOS 26. `ShelfItemView`'s × and ✓ badges hang 3pt over the chip's corners, so the selection highlight is drawn by a dedicated `highlightView` subview, not on the chip's own layer. `bgView` in the root is fine because it has no subviews.

**Within-app drops are disabled** (`sourceOperationMaskFor` returns `[]` for `.withinApplication`) so an item can't be dropped back onto the shelf itself.
